学习区

先搞清楚每个面板解决什么问题，再开始实战。

面试里最怕的不是不会优化，而是说不出“先看哪个面板、再看哪个指标、最后怎么验证”。这一页是你的速查表。

Network

看资源和请求链路

  • 首屏慢先看请求数量、体积、缓存、阻塞链
  • 重点关注 Waterfall、Size、Time、Initiator、Priority
  • 实操时先勾 Disable cache，再切 Slow 3G 或 Fast 4G
Performance

看主线程在忙什么

  • 录制刷新过程，确认是网络慢还是 JS 长任务慢
  • 重点看 Screenshots、Main、Long Tasks、Bottom-up、Call tree
  • 首屏问题核心指标常看 FCP、LCP
Memory

看对象为什么没释放

  • Heap Snapshot 适合做“某一刻”的对象盘点
  • Allocation Timeline 适合观察一段用户操作期间的增长和回收
  • 特别留意 Detached DOM、定时器、监听器、闭包和全局缓存
Lighthouse

快速体检，不是最终根因

  • 适合快速发现性能和最佳实践问题
  • 看完建议后，还是要回到 Performance / Network 验证
  • TBT 在 Lighthouse 里会很常见
Coverage

看加载了多少没用到

  • 适合发现首屏引入的无用 CSS / JS
  • 看到利用率很低时，可以联想到拆包、懒加载、按路由加载
  • 它是辅助工具，经常和 Performance 一起看
面试回答

一句话顺序

  • 首屏慢：先 Network，再 Performance，必要时加 Coverage 和 Lighthouse
  • 内存泄漏：先 Memory 做快照和时间线，再回代码看引用链
  • 最后一定要做“修复前后对比验证”

性能指标速记

指标 你可以怎么理解
FP页面第一次有像素出现
FCP页面第一次有文字、图片等真实内容出现
FMP历史指标，知道它表示“主要内容出现”即可
LCP最大首屏内容元素出现的时间，首屏体验重点指标
TBTFCP 之后被长任务阻塞的总时长
TTI页面真正稳定可交互的时间

这几个概念容易混

  • FCP 只代表“有内容了”，不代表“主要内容准备好了”
  • LCP 更贴近用户感知的首屏核心内容
  • TBT 反映的是“页面虽然开始显示了，但主线程还在卡”
  • TTI 更偏向“什么时候终于可以顺畅操作”

怎么把这页内容讲成面试回答

你不需要背很多定义，重点是把“工具负责什么”和“排查顺序”讲清楚。定义只需要说到能指导你下一步判断即可。
