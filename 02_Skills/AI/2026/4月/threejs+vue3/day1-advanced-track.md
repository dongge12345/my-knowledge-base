## 第 1 小时：Vue2 -> Vue3 深入差异

### 1. 响应式系统为什么重写

`Vue2` 主要基于 `Object.defineProperty`，它的核心问题不是“不能用”，而是“能力和维护性有边界”。

主要限制：

- 无法原生拦截对象属性的新增和删除
- 对数组下标和长度变化处理不够自然
- 初始化时需要递归遍历所有属性，初始化成本高
- 对复杂数据结构支持不够统一

`Vue3` 改成 `Proxy` 后，收益在于：

- 可以拦截新增、删除、读取、设置等更多操作
- 对数组和对象处理更统一
- 更适合懒代理和按需追踪
- 为后续性能优化和更清晰的依赖收集机制打基础

### 面试回答模板

如果被问“Vue3 为什么要改响应式”：

可以这样答：

`Vue2` 的响应式基于 `Object.defineProperty`，在对象新增属性、数组索引更新、初始化递归成本这些方面都有局限。`Vue3` 使用 `Proxy` 后，拦截能力更完整，对对象和数组的处理更统一，也更利于按需依赖收集和性能优化，所以它不是简单语法升级，而是响应式底层能力的重构。

### 2. Composition API 不只是写法变化

很多人会把 `Composition API` 理解成“只是把 data、methods、computed 换个地方写”，这在面试里不够。

更好的理解是：

- `Options API` 按配置项分散逻辑
- `Composition API` 按业务关注点组织逻辑

它的核心价值：

- 复杂组件中逻辑更容易聚合
- 更适合抽离复用逻辑到 `composable`
- 更利于 `TypeScript` 类型推导
- 更方便将副作用、状态、派生值、清理逻辑放在一起维护

### 面试回答模板

如果被问“Vue3 Composition API 的优势是什么”：

可以这样答：

它最大的价值不是语法更先进，而是让复杂组件的逻辑组织方式更合理。`Options API` 容易把一个功能拆散到 `data`、`methods`、`computed`、`watch` 里，而 `Composition API` 可以把一个业务功能相关的状态、副作用和方法放在一起，复用时抽成 `composable` 也更自然，这对复杂页面和长期维护尤其有价值。

### 3. `ref`、`reactive`、`computed`、`watch`、`watchEffect` 的边界

这是 Vue3 面试非常常见的一组题，面试官真正想看你会不会“边界判断”。

#### `ref` 和 `reactive`

经验化理解：

- 基础类型优先 `ref`
- 需要整体表达对象结构时常用 `reactive`
- 团队里很多场景会统一优先 `ref`，因为解构和传递时更清晰

面试别答成“对象用 reactive，基本类型用 ref”就结束了，这太浅。

更完整的说法：

- `ref` 包装值，语义更明确
- `reactive` 返回代理对象，适合表达结构化状态
- 组合式函数返回值为了避免解构丢失响应性，常配合 `toRefs`

#### `computed`

用于“有缓存的派生值”。

如果某个值是由别的响应式状态推导出来，而且希望依赖没变时复用结果，就适合用 `computed`。

#### `watch`

用于“明确监听某个源并在变化后执行副作用”。

典型场景：

- 监听路由参数变化重新请求数据
- 监听表单字段变化做节流校验
- 监听某个状态变化同步本地存储

#### `watchEffect`

用于“自动收集依赖并立即执行副作用”。

它适合依赖源不想手动列举，或者初始化和变更逻辑一致的场景。但依赖多、链路复杂时，可读性不一定比 `watch` 更好。

### 面试回答模板

如果被问“`watch` 和 `watchEffect` 区别”：

可以这样答：

`watch` 需要显式指定监听源，依赖关系更清晰，也能拿到新旧值，适合精确控制副作用。`watchEffect` 会在执行过程中自动收集依赖并立即执行，适合初始化和依赖变更逻辑一致的场景，但复杂场景下可读性和可控性通常不如 `watch`。

### 再进一层：flush 时机

如果想拉开层次，可以补一句：

- `flush: 'pre'` 默认，在组件更新前触发
- `flush: 'post'` 在 DOM 更新后触发，适合依赖最新 DOM 的逻辑
- `flush: 'sync'` 同步触发，通常要谨慎用

这句一说，面试官会觉得你不是停留在 API 表层。

### 4. Vue2 到 Vue3 的生命周期映射

常见映射：

- `beforeCreate/created` -> `setup`
- `beforeMount` -> `onBeforeMount`
- `mounted` -> `onMounted`
- `beforeUpdate` -> `onBeforeUpdate`
- `updated` -> `onUpdated`
- `beforeDestroy` -> `onBeforeUnmount`
- `destroyed` -> `onUnmounted`

真正重要的不是背映射，而是知道：

- `setup` 执行时组件实例还没完全建立
- 不要把 `setup` 简单理解成 `created`
- DOM 相关逻辑仍应放在 `onMounted`

### 5. Vue3 在性能上的真实收益

不要只说“Vue3 更快”，要知道快在哪。

面试能说的点：

- 编译阶段做了更多静态提升
- 通过 Patch Flags 精准标记动态节点
- 更新时减少不必要的 diff
- Fragment 支持更自然，减少无意义包裹层
- Tree-shaking 更好，产物更轻

### 面试回答模板

如果被问“Vue3 性能为什么更好”：

可以这样答：

Vue3 的提升一部分来自响应式底层重写，另一部分来自编译优化。比如静态节点提升、Patch Flags、Tree-shaking 都让运行时更新和最终产物更高效。所以它不是单点优化，而是响应式、编译器和运行时协同带来的结果。

### 6. 迁移视角：如果你从 Vue2 项目切到 Vue3，你会怎么做

这是你非常适合拿来讲经验的部分。

建议回答思路：

1. 先评估项目规模、第三方依赖兼容性、组件复杂度
2. 优先迁移公共组件和新功能模块
3. 不强行一次性重构所有老代码
4. 建立组合式函数规范、目录规范、状态管理规范
5. 联动工程升级，比如从 `Webpack` 迁移到 `Vite`

### 面试表达模板

我不会把 Vue2 到 Vue3 的升级理解成简单语法替换，而是会先评估依赖兼容性和迁移成本。对于存量项目，我更倾向于分阶段迁移，优先在新模块和公共能力上引入 Vue3 和 Composition API，在保证交付稳定的前提下逐步统一编码方式和工程规范。
